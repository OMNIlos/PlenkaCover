# Домашний beta-тест ERP на VPS через Zoom

Дата актуализации: 2026-07-21.

> Подтверждённый первый пост использует RS-232→USB `4800/even` для МАССА-К, USB/CUPS raw ZPL
> для TLP4 и 2.4G HID для SG-110-BT. Сначала прочитайте
> [полевую базу знаний](./2026-07-21-physical-devices-field-knowledge.md); она заменяет ранний
> Ethernet-путь принтера для этого комплекта.

Эта инструкция рассчитана на следующий реальный сценарий:

- PlenkaCover уже размещён на арендованном VPS;
- ведущий теста находится у себя с Mac и руководит проверкой через Zoom;
- коллега находится рядом с одним промышленным компьютером с Ubuntu;
- рядом с коллегой находятся весы МАССА-К, принтер MERTECH TLP4 и сканер POScenter SG-110-BT;
- Ubuntu-компьютер может быть практически пустым: операционная система есть, но нужные программы
  ещё не установлены;
- коллега не обязан разбираться в Linux, Docker, COM-портах или сетях.

Инструкция специально написана линейно. Не перескакивайте через шаги. После каждой строки либо
ставьте галочку, либо записывайте `STOP`, `BLOCKED` или `FAIL`.

Полная техническая инструкция для разбора нестандартных ошибок находится в
[first-hardware-smoke.md](./first-hardware-smoke.md). Текущий документ — основной сценарий
самого Zoom-звонка.

## 0. Что получится в конце

Тест состоит из четырёх отдельных результатов:

1. `VPS PASS` — сайт, API и база на VPS доступны.
2. `BROWSER PASS` — роли входят, видят правильные экраны и не получают чужие права.
3. `HARDWARE PASS` — реальные весы, принтер, сканер и Ubuntu gateway фактически отработали.
4. `BUSINESS FLOW PASS` — оператор выполнил тестовый рулон, а склад принял его настоящим сканом.

Проверка 1С записывается отдельно. Сейчас реальный HTTP-адаптер включён, но внешний endpoint
1С:Фреш возвращал HTTP `420`, поэтому текущий ожидаемый статус — `1C PENDING`, а не `PASS`.

Симулятор не нужен для этого звонка. `POST-5` и `гайнулин ильназ` (Гайнулин Ильназ) оставьте
нетронутыми. Физический тест проводится только на `POST-1` с учётной записью `ахметов булат`.

## 1. Кто что делает во время звонка

### Вы, ведущий теста

Вы работаете со своего Mac и:

- держите открытым этот документ;
- входите в ERP как `admin`, `production`, `commercial`, `finance` и `director`;
- проверяете состояние VPS;
- проверяете `POST-1` и привязки устройств;
- выпускаете gateway token для `POST-1`;
- заранее проверяете, что смена назначена оператору, но ещё не открыта;
- говорите коллеге, какую команду выполнить;
- записываете результат каждого шага;
- останавливаете тест при любой неоднозначности.

### Коллега рядом с оборудованием

Коллега:

- физически соединяет кабели;
- включает Ubuntu-компьютер и устройства;
- показывает экран Ubuntu через Zoom;
- вводит команды в Ubuntu Terminal;
- устанавливает Chromium и gateway-agent;
- смотрит на табло весов и на реально вышедшую этикетку;
- входит в ERP как `ахметов булат`, а затем как `warehouse`;
- фактически сканирует QR сканером.

### Очень желательно использовать для Zoom второе устройство

Лучший вариант:

- Zoom работает на телефоне или отдельном ноутбуке коллеги;
- промышленный Ubuntu-компьютер используется только для ERP и gateway.

Так звонок не оборвётся при перезагрузке Ubuntu, а камерой можно показать кабели, табло весов и
вышедшую этикетку. Если Zoom работает на самом Ubuntu-компьютере, заранее договоритесь, что после
перезагрузки коллега снова подключится к звонку.

## 2. Главные запреты

Перед началом прочитайте эти правила вслух.

- Не подключать весы, принтер или сканер к VPS. Они подключаются только к Ubuntu-компьютеру дома.
- Не устанавливать Docker, Node.js, Git или исходный код на промышленный компьютер.
- Не использовать `plenka-dev` и другие старые dev-пароли.
- Не отправлять gateway token в Zoom-чат, общий мессенджер, скриншот или запись звонка.
- Не показывать содержимое `/etc/plenka-gateway/agent.env` на демонстрации экрана.
- Не вводить пароль оператора в конфиг gateway.
- Не вводить gateway token в браузер.
- Не добавлять к `curl` параметры `-k` или `--insecure`.
- Не включать `simulated`, чтобы искусственно получить зелёный статус.
- Не использовать `/dev/ttyUSB0`; нужен стабильный путь `/dev/serial/by-id/...`.
- Не подключать TLP4 одновременно по USB и Ethernet без отдельного плана. Рабочий путь — USB.
- Не нажимать кнопку печати повторно, пока судьба первой команды неизвестна.
- Не вводить вес рулона руками. Вес рулона должен прийти с реальных весов.
- Не ставить на весы груз тяжелее разрешённой максимальной нагрузки.
- Не ставить seed Big-bag массой 500 кг на весы с НПВ около 300 кг.
- Не исправлять смены, назначения или команды прямым SQL.

| Кто использует    | Логин        | Для чего                               |

Если пароль любой роли неизвестен:

1. войдите как `admin`;
2. откройте раздел управления пользователями;
3. найдите нужный login;
4. нажмите штатный сброс пароля;
5. укажите причину `Подготовка домашнего beta-теста через Zoom`;
6. сохраните показанный временный пароль в закрытом password manager;
7. передайте его только конкретному тестировщику;
8. при первом входе задайте новый уникальный пароль;
9. обновите закрытое хранилище;
10. не записывайте пароль в этот runbook, Zoom-чат или test record.

Не сбрасывайте уже проверенные `commercial` и `admin` без необходимости. Не пытайтесь получить
пароль из password hash или изменить его SQL-командой.

### 3.3. Что должно лежать рядом с коллегой

#### Компьютер и сеть

- [ ] Промышленный x86-64 компьютер с Ubuntu 24.04.
- [ ] Монитор.
- [ ] Клавиатура.
- [ ] Мышь.
- [ ] Сетевой кабель для Ubuntu-компьютера.
- [ ] Домашний роутер или Wi-Fi с доступом Ubuntu-поста к интернету.
- [ ] Достаточно свободных USB-портов либо powered USB hub.
- [ ] Стабильный домашний интернет без гостевой изоляции устройств.
- [ ] Коллега знает пароль локального Ubuntu-пользователя для `sudo`.

#### Весы

- [ ] Весы МАССА-К ТВ-М-300.2-A(RUEW)3.
- [ ] Их терминал A(RUEW).
- [ ] Штатный communication USB-кабель терминала.
- [ ] Безопасный контрольный груз с известной массой.
- [ ] Пустая шпуля либо физический предмет, который будет играть роль шпули.
- [ ] Безопасный тестовый груз для рулона.

Для зелёного happy path нетто тестового рулона желательно получить около `41.2 кг`, допустимое
отклонение текущего pilot fixture — примерно ±5%. Если такого груза нет, связь с весами проверить
можно, но рулон может перейти в ветку отклонения и полный business-flow останется `BLOCKED`.

#### Big-bag для открытия смены

Нужен реально взвешенный тестовый мешок или контейнер. Он может быть тестовым, но число в ERP
обязано совпадать с фактическим показанием подходящих весов.

- [ ] Тестовый мешок/контейнер физически существует.
- [ ] Его масса безопасна для используемого прибора.
- [ ] Есть прибор достаточной грузоподъёмности.

Если реального безопасного взвешивания Big-bag нет, не вводите `500` из seed. В этом случае можно
завершить setup-тест весов, принтера, сканера и gateway, но открытие смены и полный рулонный цикл
записываются как `BLOCKED`.

#### Принтер

- [ ] MERTECH TLP4.
- [ ] Блок питания принтера.
- [ ] USB-кабель принтера.
- [ ] Этикетки `58 × 40 мм`, gap `2 мм` для рулонного теста.
- [ ] Подходящий риббон.
- [ ] В принтере установлена печатающая головка 203 dpi.

#### Сканер

- [ ] POScenter SG-110-BT.
- [ ] Родной 2.4G USB-донгл именно от этого сканера.
- [ ] Сканер заряжен.
- [ ] Руководство к сканеру сохранено на телефоне.

Официальное руководство SG-110-BT:
<https://pos-center.ru/files/downloads/instructions/instruction_sg-110-bt.pdf>.

## 5. За несколько часов до звонка: вы проверяете VPS с Mac

### 5.1. Сделать backup и server smoke

До создания новых бизнес-фактов войдите на VPS со своего Mac:

```zsh
ssh root@176.124.208.49
```

SSH может скрыто спросить passphrase ключа либо пароль VPS. Не диктуйте его в Zoom и не показывайте
Terminal коллеге.

На VPS выполните:

```bash
cd /opt/plenka/current/backend
./scripts/vps/validate-env.sh /opt/plenka/shared/pilot.env
./scripts/vps/backup.sh --check
./scripts/vps/smoke-vps.sh
```

Ожидается:

- environment validation — `PASS`;
- backup checksum и disposable restore-check — `PASS`;
- VPS smoke подтверждает HTTPS/readiness/private API/DB bindings;
- слово `PARTIAL` допустимо только из-за ещё не выполненного ручного browser checklist.

Если backup или restore-check падает, физический тест не начинайте.

Завершите SSH-сессию:

```bash
exit
```

### 5.2. Проверить сайт и API

Откройте Terminal на Mac и выполните по одной команде:

```zsh
export PLENKA_ORIGIN='https://176.124.208.49'

curl --fail-with-body --silent --show-error --write-out '\nHTTP %{http_code}\n' \
  "$PLENKA_ORIGIN/api/health"

curl --fail-with-body --silent --show-error --write-out '\nHTTP %{http_code}\n' \
  "$PLENKA_ORIGIN/api/health/ready"
```

Обе команды должны показать `HTTP 200`. Если хотя бы одна не показывает `200`, звонок по
оборудованию не начинайте. Сначала нужно восстановить VPS/API/DB.

### 5.3. Проверить основные входы

Откройте отдельное окно Chrome Incognito:

```zsh
open -na 'Google Chrome' --args --incognito "$PLENKA_ORIGIN"
```

Проверьте:

1. В адресной строке остался `https://`.
2. Нет предупреждения о сертификате.
3. Войдите логином `commercial` и актуальным паролем из строки `commercial` локального `.env`.
4. Убедитесь, что открылась роль коммерции.
5. Выполните logout.
6. Закройте все окна Incognito.
7. Откройте новое Incognito-окно.
8. Войдите как `admin`.
9. Убедитесь, что открылась административная поверхность.

Если `commercial` снова даёт `401`, не продолжайте аппаратный звонок и не перебирайте пароль
много раз. Зафиксируйте время и остановитесь из-за login throttling.

### 5.4. Проверить серверный baseline в admin UI

В admin UI:

1. Откройте «Посты».
2. Найдите `POST-1`.
3. Убедитесь, что он включён.
4. Убедитесь, что к нему привязаны ровно три устройства:
   - `scale-post-1`;
   - `printer-post-1`;
   - `scanner-post-1`.
5. Откройте «Устройства» и ещё раз проверьте привязку к `POST-1`.
6. Не считайте старый `ready` доказательством работы железа.
7. Пока агент не запущен, `offline`, `stale` или `unknown` — нормальное исходное состояние.

### 5.5. Проверить смену до входа оператора

Войдите ролью `production` либо откройте разрешённую production-проекцию:

1. Найдите смену `pilot-test-shift-001` — «Пилотное окно первого запуска».
2. Проверьте назначение `seed-operator` (Ахметов Булат) → `POST-1`.
3. Смена должна быть `planned`.
4. Назначение должно быть `planned`.
5. `lockedAt` должен отсутствовать.
6. Активной operator-on-post session быть не должно.
7. Тестовый рулон — `PILOT-PHYSICAL-ROLL-001`.
8. Тестовый Big-bag — `PILOT-BAG-PHYSICAL-001`.

Если смена уже `open`, сразу остановитесь. Повторный seed не является reset и не должен
перетирать физические факты. Не создавайте вторую смену и не исправляйте SQL вручную.

## 7. Начало Zoom-звонка: коллега проверяет пустой Ubuntu-компьютер

Попросите коллегу открыть Terminal сочетанием `Ctrl+Alt+T`.

Объясните ему:

- команда вводится целиком и запускается клавишей `Enter`;
- `sudo` спросит пароль локального Ubuntu-пользователя;
- при вводе пароля символы и точки не отображаются — это нормально;
- если появилась красная ошибка, следующую команду не вводить;
- вместо этого показать ошибку вам на экране.

### 7.1. Проверить Ubuntu и архитектуру

Коллега вводит:

```bash
. /etc/os-release
printf 'OS: %s %s\n' "$NAME" "$VERSION_ID"
uname -m
df -h / /var
```

Нужно увидеть:

- Ubuntu `24.04`;
- `x86_64`;
- несколько гигабайт свободного места в `/var`.

Если Ubuntu не загружается до рабочего стола, версия не `24.04` или архитектура не `x86_64`,
запишите `BLOCKED`. Установку/переустановку ОС не смешивайте с аппаратным beta-тестом.

### 7.2. Проверить интернет

Коллега вводит:

```bash
ip -br link
ip route
```

Нужно увидеть активный сетевой интерфейс и строку `default via ...`.

Затем:

```bash
curl --version
```

Если `curl` пока отсутствует, это нормально: он будет установлен следующим шагом.

### 7.3. Обновить системные пакеты и установить минимум

## 9. Коллега проверяет и устанавливает gateway package

### 9.1. Открыть папку с двумя файлами

Коллега создаёт папку и переносит туда полученные файлы через приложение «Файлы»:

```bash
mkdir -p "$HOME/plenka-gateway-release"
cd "$HOME/plenka-gateway-release"
find . -maxdepth 1 -type f -printf '%f\n'
```

Должны отображаться ровно один `.deb` и его `.deb.sha256`.

### 9.2. Проверить checksum

```bash
mapfile -t DEBS < <(find . -maxdepth 1 -type f \
  -name 'plenka-gateway-agent_*_amd64.deb' -print | sort)
test "${#DEBS[@]}" -eq 1
DEB="${DEBS[0]}"
test -f "${DEB}.sha256"
sha256sum -c "${DEB}.sha256"
dpkg-deb --field "$DEB" Package Version Architecture
```

Ожидается:

- checksum заканчивается `OK`;
- Package — `plenka-gateway-agent`;
- Architecture — `amd64`.

При `FAILED` пакет не устанавливать.

### 9.3. Установить пакет

```bash
sudo apt install "$DEB"
dpkg-query -W -f='${Package} ${Version} ${Architecture}\n' plenka-gateway-agent
sudo systemctl is-enabled plenka-gateway.service || true
sudo systemctl is-active plenka-gateway.service || true
```

После первой установки ожидаются `disabled` и `inactive`. Это правильно: службу ещё нельзя
запускать, пока не заполнена конфигурация.

Node.js уже встроен в пакет. Отдельно устанавливать его нельзя и не нужно.

## 11. Настроить весы, принтер и сканер до заполнения конфига

### 11.1. Дать gateway доступ к USB-COM весов

```bash
sudo usermod --append --groups dialout plenka-gateway
id plenka-gateway
```

В списке групп должно присутствовать `dialout`.

### 11.2. Найти стабильный путь весов

```bash
sudo udevadm settle
find /dev/serial/by-id -maxdepth 1 -type l -print
```

Если показан один путь, это обычно communication USB весов. Если путей несколько:

1. коллега запоминает список;
2. отключает только communication USB весов;
3. повторяет команду;
4. подключает USB обратно;
5. повторяет команду;
6. выбирает путь, который исчез и снова появился.

Путь должен начинаться с:

```text
/dev/serial/by-id/
```

Не использовать `/dev/ttyUSB0`.

### 11.3. Подключить TLP4 по USB

1. Установить этикетки и риббон по руководству принтера.
2. Подключить включённый TLP4 напрямую к Ubuntu USB-кабелем.
3. Убедиться, что принтер виден:

```bash
lsusb
lpinfo -v | grep -i mertech
```

Если Ubuntu автоматически создала TLP4 как HP DesignJet, это неправильный driver. Установить
официальный MERTECH/HT600 Linux driver для 203 dpi и удалить чужую queue.

### 11.4. Проверить CUPS queue

Рабочая queue называется `TLP4` и использует точный `usb://MERTECH/...` URI:

```bash
lpstat -p -d
lpstat -v TLP4
```

Ожидается: queue `TLP4` enabled/idle и устройство MERTECH. Не публиковать USB serial из URI.
Принтер должен быть переведён в ZPL. Plain text и GUI test page не использовать как физический
gate; проверка выполняется валидным raw ZPL и затем ERP.

### 11.5. Проверить сканер как клавиатуру

1. Переключить Ubuntu на английскую раскладку.
2. Открыть приложение Text Editor.
3. Создать пустой несохранённый документ.
4. Щёлкнуть мышкой в документ — должен мигать курсор.
5. Взять обычный тестовый QR, не barcode настройки сканера.
6. Нажать trigger сканера один раз.

PASS выглядит так:

- появилась ровно одна строка;
- строка не удвоилась;
- после строки курсор перешёл на следующую строку;
- это означает один suffix `Enter`;
- текст появился только после реального скана.

Если текст не появился, проверить заряд, родной донгл и режим `2.4G HID keyboard`. Если нет
`Enter`, использовать только официальное руководство SG-110-BT, страницы 21–22 и 31–33. Не
сканировать setup barcode от похожей модели.

Закрыть тестовый документ без сохранения.

## 13. Проверить реальные весы до запуска службы

Gateway service пока должен быть `inactive`. Standalone probe и service нельзя запускать
одновременно: они будут спорить за один COM-порт.

### 13.1. Пустые весы

1. Снять весь груз.
2. Дождаться стабильного индикатора.
3. Выполнить:

```bash
sudo plenka-gateway-probe
```

PASS:

- exit code `0`;
- `protocol` равен `massa-k-protocol-100`;
- `simulated` равен `false`;
- reading имеет `stable=true`;
- число совпадает с табло максимум в пределах одной цены деления.

### 13.2. Известный неподвижный груз

1. Поставить безопасный контрольный груз по центру.
2. Дождаться стабильности.
3. Выполнить:

```bash
sudo plenka-gateway-probe
```

Число должно совпасть с табло максимум в пределах одной цены деления.

### 13.3. Движущийся груз

Один человек безопасно шевелит контрольный груз, второй запускает:

```bash
sudo plenka-gateway-probe
```

Ожидается `unstable`, `stable=false` и non-PASS exit. Если во время движения получен стабильный
PASS, scale gate провален.

### 13.4. Отключение USB и восстановление

1. Снять груз.
2. Отключить только communication USB весов.
3. Выполнить `sudo plenka-gateway-probe` — успешного веса быть не должно.
4. Подключить кабель обратно в тот же USB-порт.
5. Выполнить:

```bash
sudo udevadm settle
find /dev/serial/by-id -maxdepth 1 -type l -print
sudo plenka-gateway-probe
```

Должен восстановиться тот же `/dev/serial/by-id/...`, а стабильный probe снова пройти.

## 20. Проверить склад на том же Ubuntu-компьютере

4. Входит учёткой `warehouse` с паролем из закрытого канала.
5. Открывает приёмку `PILOT-TEST-RECV-001`.
6. Находит ожидаемый `PILOT-PHYSICAL-ROLL-001`.
7. Кликает в пустое scan-поле.
8. Фактически сканирует ту же физическую этикетку.
9. Ожидается `accepted`.
10. Сканирует ту же этикетку второй раз только для проверки duplicate.
11. Ожидается `duplicate`, без второй записи приёмки.
12. Завершает приёмку предусмотренной кнопкой один раз.

Warehouse не должен видеть gateway token, admin raw diagnostics или финансовые действия.

## 21. Вы проверяете остальные роли с Mac

Каждую роль открывайте в новом Incognito-окне. После проверки выполняйте logout и закрывайте все
Incognito-окна.

### Commercial

- видит `PILOT-TEST-001`;
- видит независимые индикаторы производства, склада, оплаты и отгрузки;
- видит результат производства/склада после refresh;
- не видит raw device payload;
- не может менять оплату.

### Production

- видит выполненный операторский факт;
- видит назначение правильного оператора и поста;
- не может менять финансовый статус;
- login оператора не подменяется действием production lead.

### Finance

- видит тестовый финансовый заказ;
- видит parsed source snapshot, но не raw payload;
- не выполняет операторские или складские действия.

### Director

- видит агрегированные результаты и audit/drilldown;
- routine-действия других ролей не появляются автоматически;
- любой override требует причину и доказательство.

### Admin

- видит heartbeat, devices, command lifecycle и diagnostics;
- raw diagnostic boundary остаётся только здесь;
- не выполняет бизнес-операции вместо operator/warehouse.

## 22. Проверка 1С в этом beta-тесте

1. Войти как admin.
2. Открыть раздел 1С.
3. Нажать только «Проверить соединение».
4. Зафиксировать `mode`, `status` и категорию ошибки без username/password/full URL.

Текущий известный результат:

```text
mode=http
status=unavailable
HTTP 420
```

Пока статус не стал `ready`:

- не запускать import;
- не запускать write;
- не включать mock;
- записать `1C PENDING: требуется исправить OData publication URL/rights`.

Это не делает физический тест устройств неуспешным, но общий релиз остаётся `PARTIAL` по 1С.

## 23. Проверить один отказ только после happy path

Не начинайте отказные тесты, пока нормальный рулонный цикл не завершён.

Самая безопасная проверка — остановка gateway service:

```bash
sudo systemctl stop plenka-gateway.service
```

Вы наблюдаете в admin UI переход `online → stale → offline`. Затем коллега выполняет:

```bash
sudo systemctl start plenka-gateway.service
```

Проверьте новый heartbeat и возврат в `online`.

Не отключайте принтер во время незавершённой print-команды. Если связь оборвалась после отправки
байтов и неизвестно, вышла ли этикетка, не нажимайте печать повторно: это `delivery_unknown`,
который должен разобрать admin через reconciliation.

## 24. Что сохранить после теста

Можно сохранить:

- дату и UTC-время;
- backend/frontend SHA;
- версию gateway package;
- Ubuntu version;
- факт checksum `OK`;
- `POST-1 online`;
- `massa-k-protocol-100`, `simulated=false`;
- совпадение веса с табло в пределах одной цены деления;
- количество вышедших этикеток;
- факт настоящего scanner input;
- PASS/FAIL/BLOCKED каждого шага;
- краткий текст ошибки без raw payload.

Нельзя сохранять:

- пароли;
- gateway token;
- Bearer token/cookie;
- полный `/dev/serial/by-id`;
- USB serial/MAC;
- raw frame весов;
- QR payload;
- полный `agent.env`;
- DB dump;
- фото коммерческой продукции или реальных документов.

## 25. Что делать после звонка

### Если Ubuntu-пост продолжит использоваться для пилота

```bash
sudo systemctl is-enabled plenka-gateway.service
sudo systemctl is-active plenka-gateway.service
```

Оставьте `enabled/active`. Не копируйте `/etc/plenka-gateway/agent.env` в обычное облако.

### Если домашний тест закончен и пост пока убирают

```bash
sudo systemctl disable --now plenka-gateway.service
```

После этого вы в admin UI ротируете token `POST-1`, чтобы временно переданный token больше не
работал.

Не удаляйте `/var/lib/plenka-gateway`, пока не проверена судьба всех команд.

```text

Gateway package version:

BROWSER: PASS / FAIL / BLOCKED

PRINTER: PASS / FAIL / BLOCKED
SCANNER: PASS / FAIL / BLOCKED
GATEWAY HEARTBEAT: PASS / FAIL / BLOCKED
REBOOT RECOVERY: PASS / FAIL / BLOCKED
OPERATOR BUSINESS FLOW: PASS / FAIL / BLOCKED
WAREHOUSE FLOW: PASS / FAIL / BLOCKED
```

`READY` можно написать только если VPS/browser/hardware/business flow фактически прошли и нет
обязательного внешнего blocker. Если устройства прошли, но 1С всё ещё возвращает HTTP 420,
честный общий результат — `PARTIAL`, а не `READY`.

## 27. Короткая шпаргалка на одну страницу

1. Вы проверяете VPS `health/ready=200`.
2. Вы проверяете `POST-1`, три device binding и planned смену.
3. Вы передаёте коллеге `.deb` + `.sha256`.
4. Коллега проверяет Ubuntu 24.04/x86_64 и ставит `curl`, `jq`, `nc`, Chromium.
5. Коллега подключает Ubuntu и TLP4 к одному роутеру.
6. Коллега подключает USB весов и родной донгл сканера к Ubuntu.
7. Коллега проверяет checksum и устанавливает gateway package.
8. Вы выпускаете token `POST-1`.
9. Коллега находит `/dev/serial/by-id`, IP/порт TLP4 и проверяет HID-сканер.
10. Коллега заполняет root-owned `agent.env` при выключенной демонстрации экрана.
11. `--check-config` показывает `physical`.
12. Коллега проверяет весы: ноль, груз, движение, USB reconnect.
13. Коллега запускает service; вы видите `POST-1 online`.
14. Коллега перезагружает Ubuntu; service/heartbeat/devices восстанавливаются сами.
15. Вы печатаете одну setup label; коллега видит бумагу и сканирует её в Text Editor.
16. Коллега входит как `ахметов булат` и видит «Нужен старт».
17. Только после реального веса Big-bag оператор открывает смену.
18. Реальный вес шпули → реальный вес рулона → одна label → физический scan.
19. Logout `ахметов булат` → login warehouse → scan той же label → accepted + duplicate check.
20. Вы проверяете commercial/production/finance/director/admin проекции и аудит.
21. Вы выполняете только connection check 1С и честно записываете HTTP 420/PENDING.
22. После теста либо оставляете agent active, либо выключаете и ротируете token.
