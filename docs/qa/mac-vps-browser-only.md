# Mac → VPS: простая browser-only проверка без оборудования

Эта инструкция — первый и самый безопасный тест размещённой на VPS платформы с обычного Mac.
Ничего подключать к USB/COM не нужно, gateway-agent устанавливать и запускать не нужно.

Результат этого теста может быть только `BROWSER PASS/FAIL`. Он **не** доказывает работу весов,
принтера, сканера или physical gateway. Для browser-only проверки agent token не нужен и не должен
передаваться на Mac или вводиться в браузер.

## 1. Что подготовить

Нужно:

- Mac с доступом в интернет;
- актуальный Google Chrome;
- точный HTTPS-адрес платформы вида `https://<pilot-host>` из защищённой передачи владельца VPS; host может быть доменом или public IP, если сертификат выдан именно для него;
- три pilot-учётные записи из secure handoff: `admin`, `warehouse`, `гайнулин ильназ`;
- пароли к ним из того же защищённого канала.

Здесь `secure handoff` означает отдельную защищённую передачу секретов владельцем VPS, например
approved password manager/одноразовую secret-ссылку, а не Git, `.env` из репозитория или чат со
screenshots.

В документ, заметки, screenshots и команды пароли не копировать. Не использовать старый dev-пароль
из репозитория. Если для аккаунта требуется смена временного пароля, новый пароль должен быть
уникальным и оставаться только в указанном защищённом хранилище.

Не нужны:

- gateway agent token;
- Docker, Node.js или checkout репозитория;
- весы, принтер и сканер;
- доступ к SSH/VPS;
- отключение TLS-проверки.

## 2. Проверить HTTPS и readiness

Откройте Terminal на Mac. Подставьте выданный HTTPS origin без `/api`, пути и завершающего `/`:

```zsh
export PLENKA_ORIGIN='https://<pilot-host>'
curl --fail-with-body --silent --show-error --write-out '\nHTTP %{http_code}\n' \
  "$PLENKA_ORIGIN/api/health"
curl --fail-with-body --silent --show-error --write-out '\nHTTP %{http_code}\n' \
  "$PLENKA_ORIGIN/api/health/ready"
```

Ожидается:

- обе команды завершаются без ошибки;
- обе показывают `HTTP 200`;
- `/api/health` сообщает нормальный статус процесса;
- `/api/health/ready` сообщает готовность API и PostgreSQL принимать запросы.

Эти endpoints публичны и не требуют логина. Не добавляйте пароль, Bearer token или agent token в
`curl`. Не используйте `curl -k`/`--insecure`: успешная команда с отключённой проверкой сертификата
не считается PASS.

Если обе команды прошли, откройте отдельное окно Chrome Incognito:

```zsh
open -na 'Google Chrome' --args --incognito "$PLENKA_ORIGIN"
```

В адресной строке должен остаться `https://`. Предупреждения сертификата быть не должно.

## 3. Правило проверки трёх ролей

Проверяйте роли последовательно, по одной:

1. войти ролью;
2. проверить доступные ей экраны;
3. обновить страницу и проверить сохранение сессии;
4. выполнить logout;
5. закрыть **все** окна Incognito;
6. открыть новое Incognito-окно для следующей роли.

Разные Incognito-окна одного запущенного Chrome могут делить временное browser storage. Поэтому не
держите одновременно `admin`, `warehouse` и `гайнулин ильназ`: иначе можно ошибочно принять сессию одной
роли за другую.

После каждого входа:

- роль/профиль в UI должны соответствовать использованной учётной записи;
- production demo role switcher или вход через `x-role` отсутствует;
- обычный refresh (`Cmd+R`) и hard refresh (`Cmd+Shift+R`) оставляют пользователя в той же
  действующей сессии;
- чужие разделы и чувствительные действия не должны появляться только из-за изменения URL.

Если UI требует сменить временный пароль, выполните смену, затем полностью выйдите и войдите новым
паролем. Не сохраняйте пароль в screenshot или clipboard manager.

## 4. Проверка admin

Войдите pilot-учётной записью, помеченной в secure handoff как `admin`.

Проверьте без изменения данных:

1. открывается администраторская поверхность;
2. видны platform health и статус БД/API;
3. видны посты `POST-1..POST-5` и их device bindings;
4. без запущенного агента посты/устройства не должны изображаться физически готовыми: допустимы
   `offline`/`stale`/`pending`, но не hardware PASS;
5. raw diagnostics доступны только через отдельную admin-диагностику и не появляются на обычных
   бизнес-экранах;
6. demo role switcher отсутствует.

Не выполняйте account reset, token rotation, device rebind/recovery или другие admin mutations в
этом browser-only smoke.

### Проверка 1С

На admin-экране 1С можно выполнить **только connection check**. На checkpoint 2026-07-17 честный
ожидаемый результат — `mode=http`, `status=unavailable`/`PENDING`. Проверка уже развёрнутого VPS
вернула `errorCategory=network`; предшествующий прямой authenticated probe внешней публикации
возвращал HTTP `420 Not found`. В обоих случаях live endpoint пока не готов к import/write.

Это известный внешний blocker, поэтому такой честный результат сам по себе не делает browser smoke
FAIL. Ошибкой платформы было бы показать mock/HTTP `420` как успешный live PASS.

Пока check не даёт свежий `mode=http/status=ready`:

- не запускать import/retry;
- не выполнять controlled stock write;
- не менять `ONEC_LIVE` ради зелёного mock-ответа.

Затем обновите страницу, убедитесь, что admin-сессия сохранилась, и выполните logout.

## 5. Проверка warehouse

Закройте все Incognito-окна, откройте новое и войдите pilot-учётной записью `warehouse` из secure
handoff.

Проверьте только чтение:

1. открывается складской рабочий стол;
2. видны доступные warehouse-задачи/очереди и безопасная проекция остатков сырья;
3. admin accounts, token rotation и raw diagnostics недоступны;
4. warehouse не получает admin UI простым переходом по URL;
5. страница переживает `Cmd+R` без смены роли.

Не нажимайте «провести в 1С»: current read gate `PENDING`, а controlled write требует отдельного
согласованного окна и не входит в browser-only проверку. Не создавайте корректировки остатков,
приёмки или другие бизнес-факты только ради smoke.

Выполните logout и закройте все Incognito-окна.

## 6. Проверка Гайнулина Ильназа до открытия смены

Откройте новое Incognito-окно и войдите pilot-учётной записью `гайнулин ильназ` (Гайнулин Ильназ,
`seed-operator-3`, пароль `SEED_PILOT_PASSWORD_OPERATOR_3` из secure handoff). Pilot seed
резервирует для него simulator lane `POST-5`: плановую смену
`pilot-test-shift-001`, плановое назначение на пост, тестовый рулон `PILOT-SIM-ROLL-001` и
доступный Big-bag `PILOT-BAG-SIM-001`. Seed **не** открывает operator-on-post session, не
блокирует назначение и не фиксирует стартовый вес. Авторизованная browser-сессия после login и
operator-on-post session — разные сущности.

Без gateway-agent можно проверить:

1. operator runtime открывается и показывает роль `operator`;
2. рабочее место плановой смены — именно `POST-5`, а статус требует явного открытия смены;
3. UI показывает «Нужен старт», а не «Смена открыта»; стартовый вес и active
   operator-on-post session отсутствуют;
4. отображается только подготовленное тестовое назначение, без данных другого поста;
5. `PILOT-BAG-SIM-001` доступен для будущего открытия смены, но стартовый вес ещё не записан;
6. refresh сохраняет Bearer-сессию и то же плановое состояние;
7. нет поля, позволяющего вручную подставить авторитетный вес рулона вместо устройства;
8. operator не видит admin raw diagnostics, agent token и настройки другого поста.

В базовом browser-only smoke смену не открывайте: его задача — проверить HTTPS, login, роли и
честное плановое состояние без бизнес-мутации. Когда начинается отдельный simulated smoke,
оператор сам выбирает подготовленный Big-bag, вводит тестовый стартовый вес и нажимает «Открыть
смену» по инструкции `mac-vps-and-simulator-smoke.md`. Только этот явный шаг создаёт active
operator-on-post session и блокирует назначение. Для физического теста тот же шаг выполняется у
станка после фактического взвешивания Big-bag.

Без агента нельзя получить настоящий вес, напечатать бумажную этикетку или доказать физическое
сканирование. По умолчанию не нажимайте мутирующие device-кнопки.

Если владелец теста отдельно решил проверить fail-closed поведение, убедитесь, что никакой agent на
`POST-5` не запущен. Пока operator-on-post session не открыта, device-действия должны быть
заблокированы; этого достаточно для browser-only проверки. Не открывайте смену только ради
провокации device-ошибки. После явного открытия смены в отдельном simulated smoke допускается не
более **одного** согласованного device-действия. Честный `4xx/503`, timeout или команда со статусом
`failed`/`expired` не являются device PASS. Если UI показывает лишь принятие команды
(`queued`/`202`), это также не подтверждение устройства. Недопустимы fake success, придуманное
значение веса, подтверждение печати или завершение бизнес-операции без device evidence.

Не нажимайте повторно. Если команда осталась `queued`/`in_flight`, остановите тест и попросите
администратора дождаться `expired`/выполнить документированную reconciliation до запуска
симулятора. Незавершённую команду нельзя оставлять так, чтобы будущий agent неожиданно исполнил её.

Выполните logout, затем `Cmd+R` или Back. Должен снова появиться экран входа, а operator runtime не
должен открываться из browser cache.

## 7. Что считается PASS

- [ ] Оба `curl` endpoint вернули trusted HTTPS и `HTTP 200` без `-k`.
- [ ] Chrome открыл platform origin без TLS warning.
- [ ] `admin`, `warehouse`, `гайнулин ильназ` вошли только выданными Bearer-учётными записями.
- [ ] После входа UI показывает правильную роль; demo role switcher отсутствует.
- [ ] Refresh сохраняет текущую сессию и не меняет роль.
- [ ] Logout закрывает доступ: Back/refresh возвращает на login.
- [ ] Warehouse/operator не видят admin raw diagnostics или agent token.
- [ ] Без агента device path не выдал fake weight/print/scan success.
- [ ] 1С показана честно как `PENDING/unavailable`, без import/write и mock-success.
- [ ] В browser, Terminal, screenshots и Git не попали password/token/raw payload.

Если все строки выполнены: `BROWSER PASS`. При этом отдельно остаются:

- `SIMULATED PENDING` — simulated-agent не запускался;
- `PHYSICAL PENDING` — реальные устройства не проверялись;
- `1C LIVE PENDING` — внешний endpoint пока недоступен.

## 8. Если что-то не работает

### HTTP отвечает `308`, а HTTPS зависает или даёт timeout

`308` с `http://...` доказывает только доступность redirect на порту 80. Он не доказывает, что с
Mac доступен HTTPS на порту 443.

Проверьте:

1. используется ровно выданный `https://<pilot-host>`, а не другой IP/domain и не `http://`;
2. VPN не отправляет pilot host/порт 443 в неправильный tunnel;
3. split-tunnel/локальный firewall/роутер разрешают исходящий TCP 443;
4. если выдан домен, DNS в текущей сети резолвит его в ожидаемый адрес;
5. владелец VPS подтвердил firewall/reverse proxy/TLS на 443.

Повторите проверку из разрешённой сети или с корректным VPN-маршрутом. Не обходите проблему через
HTTP и не используйте `curl -k`.

### Chrome или curl предупреждает о сертификате

**STOP.** Не нажимайте «перейти всё равно», не вводите логин/пароль и не используйте `-k`. Передайте
владельцу VPS время, название браузера и текст ошибки без секретов. Тест продолжается только после
исправления доверенной TLS-цепочки/домена.

### `401` или снова появляется login

- проверьте, что выбрана правильная учётная запись из secure handoff;
- если пароль недавно менялся, используйте новый и закройте все старые Incognito-окна;
- не подставляйте `x-role` и не просите agent token;
- после нескольких неудач остановитесь, чтобы не вызвать login throttling.

### `403` или видна неправильная роль

Выполните logout, закройте **все** Incognito-окна и начните роль заново. Если `403` стабильно
воспроизводится на разрешённом этой роли экране, зафиксируйте URL/UTC/HTTP status без данных ответа
и передайте администратору. Не расширяйте capability вручную ради smoke.

### `/api/health/ready` не возвращает `200`

Это VPS/API/DB readiness blocker. Не продолжайте ролевые или device-тесты; владелец VPS проверяет
контейнеры, migrations и PostgreSQL по operational runbook.

### Нужен полный операторский цикл без физических весов

Browser-only тест его не даёт. После `BROWSER PASS` можно отдельно перейти к
[Mac → VPS simulated-agent на `POST-5`](./mac-vps-and-simulator-smoke.md). Там потребуются checkout,
Node.js, отдельное разрешение администратора и одноразовый token `POST-5`.

Результат такого прогона маркируется только `SIMULATED PASS/FAIL`. Он никогда не считается
physical/hardware PASS.
