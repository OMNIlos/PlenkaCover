## 2. Сквозной прогон по контурам (x-role, демо-данные)

В деве роль передаётся заголовком `-H 'x-role: <роль>'` (флаг `AUTH_DEV_XROLE=on`). Ожидаемые данные — из seed.

```bash
B=http://localhost:3000/api

# КОММЕРЦИЯ — 2 заказа (A-1024, R-2048)
curl -s -H 'x-role: commercial' $B/commercial/orders | jq 'length, .[].orderNumber'
curl -s -H 'x-role: commercial' $B/commercial/orders/<orderId>            # деталь заказа

# ПРОИЗВОДСТВО — очередь распределения рулонов
curl -s -H 'x-role: production' $B/production/orders
curl -s -H 'x-role: production' $B/production/roll-dispatch

# СКЛАД — задачи приёмки + остатки сырья (2 материала)
curl -s -H 'x-role: warehouse' $B/warehouse/tasks
curl -s -H 'x-role: warehouse' $B/warehouse/raw-materials | jq '.[].materialId'

# ФИНАНСЫ — заказ fo-A-1024
curl -s -H 'x-role: finance' $B/finance/orders | jq '.[].id'

# ДИРЕКТОР — очередь решений (dec-1)
curl -s -H 'x-role: director' $B/director/decisions

# АДМИН — пользователи, посты, здоровье источников
curl -s -H 'x-role: admin' $B/admin/posts | jq '.[].code'      # POST-1..POST-5
curl -s -H 'x-role: admin' $B/admin/source-health
```

**Оператор (S5)** — контур сессионный, `x-role` не даёт `userId`, нужен реальный логин:

```bash
TOK=$(curl -s -X POST $B/auth/login -H 'Content-Type: application/json' \
  -d '{"login":"ахметов булат","password":"plenka-dev"}' | jq -r .token)
curl -s -H "Authorization: Bearer $TOK" $B/operator/post-sessions/current
curl -s -H "Authorization: Bearer $TOK" $B/operator/runtime      # смена + заказы из рулонов оператора
```

**Проверка ролевой изоляции (§4):** запрос чужой роли должен давать `403`.

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H 'x-role: operator' $B/finance/orders   # ждём 403
```

### 3.2. Реальное чтение демо-1С (read-only, напрямую)

Подтверждает сущности, которые маппит `HttpOneCAdapter` (фикстуры в
`apps/api/src/integrations/onec/__fixtures__/`).

```bash
set -a && . ./.env && set +a
B1="$ONEC_BASE_URL"; A=(-sS -u "$ONEC_USERNAME:$ONEC_PASSWORD")

curl "${A[@]}" -G "$B1/Catalog_Контрагенты" --data-urlencode '$format=json' \
  --data-urlencode '$top=3' --data-urlencode '$select=Ref_Key,Description,ИНН'
curl "${A[@]}" -G "$B1/Document_СчетНаОплатуПокупателю" --data-urlencode '$format=json' \
  --data-urlencode '$top=2' --data-urlencode '$select=Ref_Key,Number,СуммаДокумента,Posted'
curl "${A[@]}" -G "$B1/AccountingRegister_Хозрасчетный/Balance" \
  --data-urlencode '$format=json' --data-urlencode '$top=2'
```

Ожидаемо: `Ref_Key`→`externalId`, `DataVersion`→`sourceVersion`. Оплаты используют **составное** `Контрагент`
(не `Контрагент_Key`), у Balance нет `Ref_Key` (см. `docs/1c-mapping.md`).

> Примечание: in-app `POST /finance/orders/:id/source-retry` рассчитан на мок (наши id заказов —
> не 1С `Ref_Key`), поэтому при `ONEC_LIVE=true` живой pullInvoice по нашему id ожидаемо не найдёт счёт.
> Это дев-артефакт; семантический обмен — на проде.

## 4. S8 — 1С-ЗАПИСЬ (обязательная) ⭐

Единственная запись платформа → 1С: остатки сырья → проведённый `Document_ОприходованиеТоваров`
(в этой БП нет регистра `ТоварыНаСкладах`, склад на счёте 41). Реализованный контракт безопасно
отказывает в mock-режиме и требует `ONEC_LIVE=true`, `ONEC_WRITE=true`, exact confirmation,
`mode=http/status=ready` и непустой snapshot.

Live write выполняется только по `docs/operations/vps-pilot-runbook.md` §7.2:

1. реальный warehouse Bearer-login — `x-role` запрещён;
2. `GET .../raw-materials/onec-push-preview` и ручное подтверждение `snapshotHash`/строк;
3. новый UUIDv4 `operationKey`;
4. один `POST .../raw-materials/push-to-1c` с JSON `{operationKey,snapshotHash}`;
5. проверка echo hash, `mode=http`, `documentCreated=true`, `accepted=true`, count/ref и ручная
   сверка одного `Posted=true` документа в 1С.

Контур дедуплицирует `operationKey` и `snapshotHash`. `outcome_unknown`, timeout, `409` с требованием
reconciliation или неоднозначный ответ запрещают retry с тем же **или новым** ключом до ручной
сверки. Историческая проверка 2026-07-02 не является текущим PASS; на 2026-07-17 S8
`PENDING / DO NOT RUN`, пока read gate возвращает HTTP `420`.

«Удаление помеченных объектов» в 1С их уберёт. Тестовые документы: `КП00-000001..NN`,

```bash

  -X PATCH "$B1/Document_ОприходованиеТоваров(guid'$REF')?\$format=json" --data '{"DeletionMark":true}'
```

### 9.2. Ручной цикл (UI)

1. **Склад** (`warehouse`/plenka-dev): мешки создаются `POST /api/warehouse/big-bags`
   `{materialId, weightKg}` — остаток сырья списывается (событие `audit:bigbag_created`).
2. **Оператор**: вкладка «Смена» → карточка Big-bag (поиск по названию/сырью) → стартовый
   вес → «Открыть смену». Справа — «Заказы смены», выработка (кг гранул), оценка времени.
3. Пайплайн рулона: строка в «Рулоны и заказы» → Принять → вес шпули → вес рулона →
   Напечатать QR (самодостаточный JSON, в UI показывается меткой «QR · <рулон>») →
   Сканируйте QR → Передать на склад. На шагах взвешивания в панели работают
   **интерактивные весы**: поллинг `GET /api/operator/scale/reading` каждые 2 с показывает
   живой вес с весов поста через gateway (симулятор: шпуля 2.0 кг, брутто 43.4 кг);
   статусы «Стабильное значение / Стабилизация / Весы недоступны». Фиксация веса —
   отдельной кнопкой, как и раньше. Вкладки «В работе»/«Ожидают» скрыты по промпту.
4. **Склад / Приёмка**: скан HID-клином (или кнопка «Сканировать QR» + вставка payload) —
   система сама открывает заказ рулона и подсвечивает строку. Статусы: принят / брак /
   в резерв + производство / ждёт производства. «Перевзвесить» с перевесом >10% плана →
   свободный резерв + замещающий рулон в производство. «Брак» → вторсырьё
   (`rm-secondary-…`) + проблема завпроизводства.
5. Палетный лист: черновик → печать (принтер поста) → скачивание docx/pdf/xlsx
   (`GET /api/warehouse/pallet-lists/:id/export?format=…`). «Закрыть приемку» — только
   когда все QR обработаны (иначе 409).
6. **Оператор**: «Сдать смену» → финальный вес КАЖДОГО мешка → анти-фрод баланс
   (yield 0.95, допуск 2%): расхождение → `problem:shift_balance_mismatch` у
   завпроизводства (`GET /api/production/problems?status=open`).
7. Брак у оператора: «Брак…» → рулон в «Отложены», проблема у завпроизводства; resolve:
   `POST /api/production/problems/:id/resolve {resolution: rework|writeoff}` — rework
   создаёт замещающий рулон `-R1`, вес брака приходуется во вторсырьё.
